# v2.5 阶段 3A 实施记录

> 状态：实现已收口，待本批提交后的 Docker runner 恢复门禁确认
> 更新日期：2026-07-30

## 1. 本批交付

- SQLite schema 从 v3 升级到 v4，新增 `memory_records`、`memory_operations`、
  `memory_snapshots`、`memory_snapshot_items` 和 `memory_links`；
- v3→v4 升级先生成带 SHA-256 的 SQLite 备份，schema migration 继续执行 checksum
  校验；受保护回滚会按依赖顺序移除 v4 表和旧表新增索引；
- 新增领域无关的 `MemoryDraft`、`MemoryRecord`、`MemorySnapshot`、`MemoryLink` 和
  写入结果契约；
- `MemoryStore` 支持事务化创建、语义复用、冲突记录、乐观版本修订、软删除、按作用域
  查询、不可变 TaskRun 快照和同项目资源关联；
- `MemoryPolicy` 限制摘要/键/来源长度，拒绝密钥和宿主路径，校验时间、置信度、
  user-confirmation 消息 hash，并把低于 0.70 的记录排除在上下文选择之外；
- 读写始终使用 Host 注入的 `Principal`，项目 viewer 只能读取，subject 记忆只对本人
  可见；跨 tenant、project、conversation、source 或 link target 均 fail-closed；
- 同一语义键的不同内容进入 `conflict`，不会静默覆盖 active 版本，也不会进入新快照；
- 写入、修订和删除使用项目内幂等键；同键不同请求稳定拒绝；
- 每个新 TaskRun 在进入 Planner 前创建或恢复唯一记忆快照；恢复同一 run 时继续使用
  原快照，即使记忆随后被修订或删除；
- Agent system context 只接收快照中的有界摘要，并显式声明 Memory 不能作为数值、
  统计、Artifact 或知识来源 Evidence；
- MCP Host metadata 新增 `memory_snapshot_id` 和 `evidence_ledger_version`，Server 只得到
  引用与版本，不得到完整项目记忆；stdio 与 Streamable HTTP 继续使用同一契约。
- Memory 创建、冲突、修订、删除、关联、快照和策略拒绝均发出结构化治理审计；事件只含
  ID、版本、状态、policy 和拒绝类型，不记录记忆正文、原始行或凭据；
- 新增 SQLite/Dataset/Artifact 离线一致备份，manifest 固定 schema v4 migration
  checksum、控制面表行数和所有文件 SHA-256；恢复前全量验证，并在覆盖前保存 quarantine；
- `/health/ready` 增加 SQLite `quick_check`、schema、v4 checksum 和 Memory 表检查，
  任何漂移均 fail-closed；
- Compose E2E 已接入 TaskRun + MemorySnapshot + Artifact 联合破坏/恢复探针，恢复后还会
  复核原报告只有一个 `step.completed`，paused 探针任务没有工具调用。

## 2. 不变量

1. Memory 是上下文导航，不进入 `evidence` 表，也不能作为 Claim 的 `evidence_id`；
2. 身份、tenant、project 和 subject 不接受模型参数覆盖；
3. conflict、superseded、deleted、expired、future 或低置信记录不进入新快照；
4. 快照仅冻结已治理摘要和血缘元数据，不复制原始消息或完整工具结果；
5. 运行中的 TaskRun 不因后续记忆变化而改变 `content_hash` 或上下文；
6. 模型和 MCP Server 没有通用 `memory.write` Tool；
7. SQLite 仍由 API/Host 单写入，不新增共享写入进程。
