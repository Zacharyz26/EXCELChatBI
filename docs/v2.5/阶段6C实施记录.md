# 阶段 6C 实施记录：受控候选假设与结果驱动探索

> 状态：6C-1～6C-4 本地实现完成，等待真实 Compose/完整 CI 签字
> 更新日期：2026-08-12
> 前置：阶段 6B 已由提交 `6b89ef6` 的完整 CI 关闭

## 1. 阶段目标

阶段 6C 在 6A 的固定 capability 目录、共享预算、数据版本、取消树和 Evidence Ledger，
以及 6B 的数据角色门禁上，开始把开放式“分析这份数据”收敛为受控探索。系统先提出少量
可证伪的候选假设，披露筛选依据并等待用户选择；候选未经工具验证前始终是 `tested=false`，
不能作为结论、Claim 或报告依据。

## 2. 6C-1 有界候选与确定性筛选

- 新增严格 `chatbi-hypothesis-screening-v1` 契约，每轮最多四个固定类型候选：趋势、异常、
  分组对比和相关性；候选按稳定优先级排序，ID 绑定数据版本、数据集、类型、capability 与
  字段角色，不由模型自由扩张；
- 筛选只消费已持久化 DataProfile 与 TaskRun 冻结 capability 目录，不读取原始行；输出固定
  `raw_rows_read=false`，并分别标记 `eligible`、`needs_confirmation` 或 `rejected`；
- 时间、指标和维度只使用 6B 的确定性角色推断。角色不足、画像不可用、能力未启用或多数据集
  未明确选择时失败关闭，不静默挑列、跨数据集或绕过 profile；
- 所有候选固定 `tested=false` 并描述预期 Evidence。筛选通过只表示“可以验证”，不表示假设
  成立，也不产生数字 Claim。

## 3. TaskRun 与人机协作接入

- 开放探索请求先生成筛选契约，再由既有 Planner 创建零执行步骤的阻塞澄清计划；
  `hypothesis_request` 把候选绑定到计划版本和当前 `data_version_hash`，答案 schema 只允许选择
  本轮通过门禁的候选陈述；
- 完整筛选结果写入 `plan.created` 的 Planner 审计并投影到 TaskSnapshot，后续状态转换和进程
  恢复不会丢失；TaskRun 详情 API 提供独立 `hypothesis_screening` 投影；
- React 协作面板显示全部候选、通过/待确认/拒绝状态、capability 与预期 Evidence，并明确
  标注“尚未验证，不是分析结论”；只有 `eligible` 候选可以填入澄清答案；
- 用户确认后复用现有 clarification → 不可变计划修订 → Executor → Evidence Ledger →
  Verifier 链路，不新增旁路执行器，也不让 MCP Server 自行递归探索。

## 4. 当前验证

- 候选契约单测覆盖稳定 ID、有界数量、能力不可用、角色不足、多数据集未选择和具体分析请求
  不触发平行假设状态；
- Agent 集成回归覆盖零模型/零工具执行的澄清、答案 enum、计划审计、TaskSnapshot 与数据版本
  一致性，并覆盖选中候选从 Plan/Invocation/Evidence Ledger 到 Verifier `PASS` 的终态投影；
- 修改范围已通过 Ruff 全库检查、修改模块严格 mypy、前端 TypeScript、生产构建与 Chromium E2E
  （13 passed、1 skipped，含 6C 跟进交互）；CI 等价的 `hashing/lexical/local` 配置下完整后端
  为 618 passed、2 skipped，14 场景 6C-4 强制评测通过。当前环境没有 Docker CLI，真实
  Compose 执行只能由远端 CI 签字，不能以静态检查替代。

## 5. 6C-2 结果绑定与状态转换

- 新增严格 `chatbi-hypothesis-execution-v1` 投影，把选中的 hypothesis ID、数据版本和
  capability 绑定到唯一的不可变 Plan/TaskStep；可执行计划缺少对应能力或重复声明能力时
  事务失败关闭，不生成悬空验证状态；
- Invocation 启动、策略拒绝/工具失败、Evidence 写入和 Evidence Ledger sequence 都在原有
  TaskStore 事务内推进同一投影。事件只公开最小状态，完整绑定保存在 TaskSnapshot，并由
  TaskRun 详情 API 和 React “假设验证链”展示；
- 趋势、异常、分组对比和相关性的原始结果由确定性解释器映射为 `evidence_outcome`；取得
  Evidence 后仅进入 `evidence_collected`，最终 `outcome` 仍为 `untested`，不得提前把工具
  输出当成结论；
- 只有 TaskRun 完成且 Verifier 为 `PASS`，状态才转换为 `supported`、`not_supported` 或
  `inconclusive`。验证失败但已有证据保持 `partial`，无证据失败为 `failed`，用户取消为
  `cancelled`，三者不会被折叠；
- 失败后的不可变计划修订可以重新绑定同一候选并保留历史 Invocation/Evidence 引用；已经
  得出终态的候选不会被后续计划静默改写。

## 6. 6C-3 结果驱动跟进

- 新增严格 `chatbi-hypothesis-followup-v1` 契约，只消费终态 hypothesis execution、原候选
  screening、持久化 Observation、TaskRun 预算/计划版本和取消根节点；不读取原始数据，也不
  接受模型自由生成跟进动作；
- 确定性策略固定为四类：候选已获支持或任务取消时 `stop`；未获支持时从相同数据集/数据版本
  的剩余 `eligible` 候选中按稳定优先级最多提出一个 `propose_next`；最近 Observation 明确
  `retryable=true` 且仍有工具/重规划余量时才 `supplement_evidence`；其余不充分、不可重试或
  上下文不一致状态一律 `degrade`；
- `max_replans` 进入 TaskRun 持久预算，工具余量同时以共享 execution scope 和实际 Invocation
  次数为准；任一预算耗尽、候选集合穷尽或取消树进入 `cancel_requested` 都会收敛，不能继续
  自动探索；
- 跟进投影与导致终态的 TaskEvent 在同一事务内落盘，并由 TaskRun 详情 API 与 React “结果
  驱动跟进”区域展示。契约固定 `automatic_execution=false`，可执行建议只会填入现有分析分支
  草案，必须由用户再次确认创建分支，不会直接调用工具；
- 单测覆盖停止、下一候选、可重试补证、预算耗尽降级、不可重试降级、取消优先和契约交叉字段
  失败关闭；TaskStore 集成回归覆盖 Verifier 终态与事件审计，Chromium 交互覆盖建议展示和
  人工填入分支目标。

## 7. 6C-4 发布门禁

- 冻结 `hypothesis_exploration_eval_set.jsonl` 的 14 个领域中立匿名场景，覆盖四类候选、角色与
  capability 缺失、候选穷尽、支持/不支持、可重试补证、不可重试降级、工具/重规划预算耗尽
  和取消收敛；用例只含 DataProfile 元数据和合成结构化结果，不保存原始行；
- `hypothesis_exploration_eval.py` 通过真实 screening、plan binding、Evidence outcome、Verifier
  finalization 和 follow-up 实现执行整条确定性链。门禁要求筛选契约、选择绑定、Evidence 结论
  和跟进决策准确率以及边界收敛率全部为 100%，未验证结论与自动执行违规数都为 0；
- 评测报告只输出 case ID、计数、状态和集合 hash，固定声明不含列名、候选陈述、数据集引用、
  Evidence payload 或资源 ID；同时固定 `reads_raw_rows=false`、`model_calls=0`、`tool_calls=0`；
- CI backend job 已接入 `--enforce` 强制门禁，并上传脱敏 `hypothesis-exploration` JSON 产物；
- 真实 Compose 浏览器门禁新增“开放探索 → 选择异常候选 → stats MCP → Evidence Ledger →
  Verifier PASS → 未支持 → 建议一个趋势候选”全链路，验证建议只填入分支草案，未确认前不会
  创建子 Run；确定性 model fixture 同时断言异常工具只请求一次；
- Compose 脚本在初次执行、API/stats-tools/report-tools/Web 重启后及离线备份恢复后三次复核
  screening/execution/follow-up 的数据版本、Invocation、Evidence、Ledger、Verifier 和终态事件，
  并检查 `automatic_execution=false` 及异常调用 exactly once。

## 8. 关闭条件与后续边界

1. 只有包含新匿名评测、完整浏览器回归和真实 Compose 三次恢复复核的远端 CI 全绿后，才能
   把本记录改为“已关闭”并补充提交及 CI run 证据；当前仅为本地实现完成；
2. 预测和多数据集 Join 仍是阶段 6 的后续独立切片，6C 不会借“候选假设”提前启用。
