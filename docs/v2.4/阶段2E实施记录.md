## 1. 本批目标

阶段 2D 已把 Executor 切到规范 MCP Client Gateway，但仍连接一个逻辑端点。2E 把该端点
拆为真实生产结构：

```text
Host → data / stats / chart / report / knowledge
```

本批不扩展 Planner、审批、长期记忆、外部 MCP 动态发现或多实例状态。

## 2. 五服务与路由

- `mcp_servers/common/service_catalog.py` 是固定服务—工具映射的单一来源；
- Registry 为每个服务创建独立 SDK session、Bearer 凭据、发现结果、健康代次和重连状态，
  不把五个目录拼成一个伪远端目录；
- Server 直接发布同一份 11 个 Agent Tool 契约，画像、血缘和报告组装不退回名称不一致的
  15 个底层工具；
- 数据集变换计算在 data-tools，衍生血缘由 Host 在结果返回后登记，保持 SQLite 单 writer；
- Server 校验签名上下文后，再检查 project/conversation/dataset 归属；跨项目引用返回稳定
  `project_scope_violation`。

## 3. Compose 安全与存储

- 根 Compose 默认 `APP_ENV=production`、Bearer API，只发布 Web 8080；
- API 和 MCP 服务位于 `internal: true` 网络，Web 不代理 `/mcp`；
- 五个服务 token 分别由 Compose secret 文件注入，上下文签名使用第六个独立 secret；
- 仓库中的 `.dev` 文件只用于本地空环境启动，生产 example 要求外部绝对路径；
- `storage-init` 先迁移 SQLite；API 等待五个工具 readiness；
- DB/upload/dataset/artifact/KB 分卷，按服务最小化 RO/RW；SQLite 因 WAL `-shm`
  协调挂载可写目录，但 MCP 服务连接固定为 URI `mode=ro`；
- 容器非 root、只读根文件系统、no-new-privileges、cap-drop、PID/CPU/内存限制和优雅退出。

## 4. 容器浏览器门禁

`compose.e2e.yaml` 只增加一个确定性 OpenAI-compatible 模型进程。它替代外部模型波动，
不替代产品 API/MCP/tool/store/files/Web。`scripts/run_compose_e2e.sh`：

1. 从空卷启动生产结构；
2. 浏览器登录并上传真实 XLSX；
3. 生成持久 TaskPlan，经 report-tools 的真实 Streamable HTTP session 产出报告；
4. 从 TaskEvent API 断言 `Evidence + Artifact + completed run`；
5. 下载真实 PDF；
6. 重启 API/report-tools；
7. 断言报告副作用只提交一次，PDF 仍可下载。

CI 的 containers job 复用已构建镜像执行该门禁；失败时输出完整 Compose 日志并上传 E2E
产物。`/chat/stream` 同时通过 `X-ChatBI-Run-ID` 响应头提供关联 ID；浏览器门禁读取响应头，
而不是对仍在传输的 SSE 调用 `response.text()`。

## 6. 首轮 CI 诊断与修复

最近三次 push 的 containers job 有两类不同失败：

1. run #7（`62f638e`）和 #8（`206df16`）在 API 非 root smoke 失败。API 镜像默认
   `APP_ENV=production`，旧 smoke 未提供生产 Bearer 配置，进程在配置校验阶段退出。
   当前 smoke 显式使用 `APP_ENV=development`；run #9 已证明 API/Web 镜像构建和两个
   非 root smoke 均通过。
2. run #9（`62870a9`）进入 Compose 浏览器门禁后失败。上传的 Playwright trace 证明
   `/api/chat/stream` 已返回 `200 text/event-stream`，但测试监听器对活动流调用
   `response.text()`，Chromium 报
   `Network.getResponseBody: No data found for resource with given identifier`，未处理的
   Promise rejection 随即终止测试。当前门禁改为从响应头读取 `run_id`，从真实 PDF
   下载请求取得恢复路径，不再消费第二份 SSE 响应体。

诊断同时发现确定性 E2E 模型与生产 Planner 的潜在下一阻塞：用户要求把“已完成的数据画像”
组装为报告时，旧 Planner 仍规划 `data.profile → report.generate`，而已有 profile Artifact
已经满足前置物料。当前仅在已有工件复用语境中跳过画像步骤；用户明确要求“重新分析”时仍保留
画像重算。该边界已由正反回归覆盖。

后续提交 `fb289b0` 修复 Compose E2E 的报告卡片定位，最新 GitHub Actions run 全绿，
证明 API/Web 镜像、非 root smoke、五服务 Compose、浏览器主链路和重启恢复门禁均已通过。
本机无 Docker CLI 的事实不再阻塞 2E，因为容器验收明确由 CI Docker runner 承担。
