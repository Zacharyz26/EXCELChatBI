## 2. 依赖图 Executor

- 每个模型轮次都从当前活动计划版本重新读取 TaskStep，不使用内存中的过期步骤状态；
- 只有 `pending` 且所有依赖均为 `completed`/`skipped` 的步骤进入 ready frontier；
- 本轮只向模型暴露 ready frontier 对应的 capability 工具定义；
- 工具调用必须绑定到“本轮开始时已开放且当前仍 ready”的具体持久化步骤，同一 ready
  步骤不能在一轮中被重复消费；
- 计划中存在该 capability 但依赖未满足时返回 `step_dependencies_unmet`；计划从未声明
  该 capability 时返回 `tool_not_in_plan`；
- `failed`/`blocked` 不会满足依赖，未知依赖也按 fail-closed 处理；
- 模型提前给最终答复时，Verifier 的补执行提示按“计划版本 + 当前 ready frontier”
  去重，不再用一个全局重试次数覆盖所有多步阶段。

## 3. Observation 驱动 Replanner

### 3.1 失败恢复

`tool_execution_failed` 和 `tool_postcondition_failed` 且 `retryable=true` 时进入：

```text
running → planning → plan.revised → running / blocked
```

- `retry`、`correct_parameters` 使用确定性修订，保留同一计划结构并把失败步骤在新版本中
  重置为 pending；
- `use_alternative_capability`、`degrade_method`、`request_clarification` 才调用受约束
  LLM Replanner；
- `block` 或没有可用模型恢复路径时生成显式 blocked 计划版本并终止；
- 每次修订记录 Observation ID/code、修订原因、Planner 路由和审计 hash；
- 自动重规划有独立次数上限，超限进入 `replan_budget_exhausted`，不会无限循环。

传给模型的上下文只包含当前计划、步骤状态、TaskContract、最小化数据集/Artifact 摘要和
有界 Observation 摘要；不包含原始工具结果、原始行或文件路径。

### 3.2 计划版本安全

- 计划修订写入新的 `task_plans`/`task_steps` 记录和 `plan.revised` 事件，不原地修改旧版本；
- 已 `completed`/`skipped` 的逻辑步骤不能删除或改变定义，其状态和时间戳复制到新版本；
- 失败步骤及其他未完成步骤在新版本中重新进入 pending，只有 Replanner 明确指定时才能
  变为 `skipped`/`blocked`；
- 同一逻辑步骤跨计划版本累计 invocation attempt，重试事件可显示 attempt 1、2……；
- 旧版本、Invocation、Evidence 和 Artifact 保留，修订不能改写已发生事实。

### 3.3 成功 Observation 条件分支

当前先实现一个确定性、高置信分支：`anomaly_detect` 明确返回零异常时，直接依赖该检测
且 capability 为 `dataset.transform` 的 pending 步骤在新计划版本中标记为 `skipped`。
前端收到 `plan.revised` 后会保留 completed/skipped/failed/blocked 的真实状态，不再把
所有修订步骤重新显示成 pending。
