## 2. 阶段 2A 已实现范围

### 2.1 生产混合 Planner

- fast、template、LLM 三条路径统一输出 `TaskPlan` schema v1；
- 路由只读取用户请求和最小化上下文，不读取评测标签；
- LLM Planner 只接收 TaskContract、列名/行列数、Artifact 摘要和实际注册的
  capability catalog，不接收原始行、文件路径或 Artifact 正文；
- LLM 输出严格 JSON，确定性校验失败只允许一次结构化修复；
- 阻塞歧义形成无步骤、带 blocking clarification 的持久化计划；
- 无工具步骤的简单对话走快速路径，不再无条件暴露全部工具。

### 2.2 计划和步骤持久化

- 每个计划版本写入既有 `task_plans`，步骤写入 `task_steps`；
- 保存计划、增加 `plan_version`/`state_version`、追加 `plan.created` 或
  `plan.revised` 事件、更新 Agent 快照在同一事务完成；
- 逻辑 `step_id` 只在计划内唯一，数据库使用独立不透明主键，支持不同任务和
  不同计划版本复用相同逻辑名称；
- TaskRun 查询接口返回活动计划与步骤状态，历史版本保留用于后续 Replanner。

### 2.3 生产执行约束

- API 生产路径把同一个模型网关同时传给 Planner 和 Executor；
- Executor 只获得当前计划 capability 可解析出的工具定义；
- 模型即使返回未规划工具调用也会被 `tool_not_in_plan` 拒绝；
- Invocation 绑定持久化 TaskStep，开始/成功/失败同步更新步骤状态；
- 确定性 Verifier 检查计划步骤；存在 pending/running/failed/blocked 步骤时
  不允许任务成功，并只提供一次按计划补执行机会；
- 计划约束默认 fail-closed，即使 LLM Planner Gateway 缺失、复杂请求降级到确定性模板，
  仍只暴露计划工具；仅冻结 v2.3 对照基线显式传入 `enforce_plan=False`。

### 2.4 前端兼容

- Web 能消费 `plan.created`/`plan.revised` 生命周期事件；
- 计划卡显示步骤目的、能力和初始状态；
- `tool_start`/`tool_end` 通过逻辑 `step_id` 更新对应计划步骤；
- 收到结构化计划后忽略旧的临时工具调用计划卡，避免重复展示。
